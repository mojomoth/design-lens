# Design Lens 0.4.0

**Release prepared locally.** These notes describe the implementation in this checkout. They do
not assert that a 0.4.0 package, tag or GitHub release has been published.

## Why this release

A four-arm comparison built one Korean public-program landing page from a technology-lab
reference. Two arms used the 0.3.0 plugin and two used the same models without it. Both plugin
arms scored lower, mainly on reference fidelity: the reference's display typeface form, corner
marks, clipped-corner buttons, carousel chrome, marquee hero and light closing band were lost;
builds added full-bleed dark bands and fonts no document specified; a direction was chosen before
the analysis existed; and verification missed dead tabs, stand-in links, a covered CTA, a solid
white icon, a masked overflow and invented numbers. The experiment had one run per arm and LLM
judges, so it guides rather than proves; the baseline is summarized in the
[0.4.0 evaluation record](../../plugin/cli/test/evaluations/0.4.0/README.md). ADR-030 records the
decisions.

## Signatures, typeface forms and tone in DESIGN.md

`DESIGN.md` keeps its twelve sections, six recipes and measured observations, and adds three
required tables:

- `### Typeface forms` classifies each type role by the glyphs in the original screenshot
  (pixel, stencil, square-terminal, techno, grotesk, mono, …) and lists open-licensed substitutes
  of the same form class. A family name and size alone no longer describe a face: validate-design
  requires a row whose Role names the display face (display, heading, headline, title or hero, or the Korean 디스플레이, 헤드라인, 제목, 타이틀, 히어로) and
  fails a Form features cell that only repeats the source or substitute family, or that names
  fewer than two distinct form features from an English/Korean vocabulary (listed in LENSES.md).
- `### Tone budget` copies pixel-measured shares from the new `tone` command: light, mid and dark
  pixels of each source full-page screenshot, full-bleed dark bands, and how dark is used (none,
  tiles, bands, mixed). CSS declaration counts remain non-area evidence.
- `### Signature priority` ranks five to ten devices that make the reference recognizable, each
  with a Kind, cited measured or tone rows, a transfer decision and a build check. The old
  "two or three signature moves" guidance is gone, and What NOT to Copy may not silently remove a
  ranked device.

```bash
~/.design-lens/bin/design-lens tone .design-lens/example-com
~/.design-lens/bin/design-lens validate-design .design-lens/example-com --json
```

## Directions, design basis and build contract in VARIATIONS.md

`## Signature retention` records every direction's decision (keep, adapt, substitute, drop) for
every ranked signature; validate-design scores each direction and fails when none retains the top
signatures (score below 0.75). Dropping a rank 1–3 device needs a verbatim brief or content quote.
`## Selected direction` records the `**Design basis:**` hash of the three DESIGN tables, so a
direction chosen before the analysis settled is detected, and a `### Build contract`: build mode,
fonts, display fonts, dark-area maxima bounded by `tone.json`, and `check:<rank>` computed-style
assertions such as `h1, h2 :: font-family ~ Orbitron`. After build QA, `## Reference fidelity`
records a verdict per signature against the newest confirmed QA run. The validation report moves
to schemaVersion 2 with `documents`, `variationScores` and `referenceFidelity`; existing checks
keep their ids and outcomes. These numbers are deterministic consistency gates, not design scores.

## Build modes

`build-from-design` defaults to `derive`: new markup from the analysis and no clone files in the
build. `clone-base` runs only on an explicit request: the editable clone is copied into the target
once, its captured images, fonts, icons and media are deleted, all text and imagery are replaced,
and the skeleton, grid, layout stylesheets and `data-dl-id`s stay. The study clone is untouched.
Lineage is measured by `qa`, never self-reported. Both brand checklists are now identical and add:
before deploying a clone-base build, rewrite the retained captured markup and stylesheets or
confirm the right to reuse them.

## Measured build QA with confirmed viewing

```bash
~/.design-lens/bin/design-lens qa --dir ./dist --project .design-lens/example-com --content CONTENT.md --brand "Example"
~/.design-lens/bin/design-lens qa-confirm .design-lens/example-com/qa/<runId> --codes <code-1>,<code-2>
```

`qa` opens the build at each captured viewport and reports `navigation` (an HTTP error page), `dead-control`, `stand-in-link`,
`fixed-overlap`, `horizontal-overflow`, `clipped-content`, `solid-icon`, `unsourced-number`,
`broken-image`, `font-readiness`, `request-failed`, `source-asset`, `source-text`,
`brand-residue`, `font-drift`, `tone-drift` and `signature-check` findings plus measured lineage.
Probes include open shadow roots; display headings are also checked for glyphs a platform
fallback font paints (for example Hangul under a Latin-only display face). A run is `fail`, `unverified` (a status-affecting check was
skipped, for example without `--content`) or `pass`; only `pass` exits 0. Review images (tiles,
viewport shots and REFERENCE/BUILD compare sheets) each carry six code characters drawn into the
pixels; `qa-confirm` writes `review.json` only when every code matches, and validate-design
requires the run cited in Reference fidelity to be the project's newest QA run, made with
`--project`, confirmed, and run against the current Build contract and mode. The skills require fixing
every fail, viewing every review image and validating without fail before claiming completion.

qa.json also records, per viewport, how many controls were candidates, clicked, live, dead or
skipped, and console errors carry their script location. Compare sheets draw the reference and the
build at one common scale. Two warning rules were narrowed after the evaluation: a bar pinned to the
viewport top that covers under 5% of a control (and not its centre) is not reported, and the
"five labels share one URL" warning applies only to a bare site root.

## Lighter inspection and traceable runs

`inspect --lite` returns compact elements, `--selector <css>` targets CSS matches in the document
and open shadow roots, and `--viewports` measures several sizes in one run. Flagless inspect output
is unchanged. Each command except `setup` and `runlog` appends one line to the local `.design-lens/RUNLOG.jsonl` (agent role
from `DESIGN_LENS_AGENT`, exit code, duration, phases; review codes redacted); `runlog --mark`
adds phase boundaries and `runlog --summary` aggregates them. `--event abort` closes an interrupted
window, which the summary reports apart, and verdict commands (qa, qa-confirm, validate-design,
fidelity, verify) record a `verdict` so verdict exits are counted apart from errors. The log is
opt-out (`DESIGN_LENS_RUNLOG=off`) and never transmitted.

## Capture stabilization

`clone` gains `--media <remote|poster|include>` (default `poster`), `--lazy-images <eager|native>`
(default `eager`), `--readiness-ms` (5000), `--readiness-retries` (2), `--capture-attempts` (2) and
opt-in `--freeze-timers`. Painted videos become their captured frame or poster, recorded in
`manifest.substituted[]`; SMIL and marquee animations are paused; repeated state changes are
retried and summarized. Disclosures appear in REPORT.md (`Substituted (not remote)`,
`Disclosed:`), evidence and fidelity; they keep a capture complete, and motion is never verified.
`--media remote` restores the 0.3.0 media behavior. `<noscript>` content stays unrendered during
paused screenshots: since 0.3.0, disabling scripts for a screenshot could make it visible and shift
the rest of the page, which a later capture attempt then accepted as consistent. Fidelity masks the
boxes of stopped marquees in the pixel comparison (their geometry is still compared). Fidelity
thresholds and negative controls are unchanged.

The [evaluation record](../../plugin/cli/test/evaluations/0.4.0/RESULTS.md) has the details:

- On the four builds of the baseline experiment, `qa` found all 12 known defects at the right
  viewports, with no false fail; the invented cohort captions in the two better builds also fail.
  `tone` separates the dark-band builds from the reference by full-bleed share (0 against 0.11 or
  more).
- A live recapture of the reference went from incomplete captures with 16 warnings each (0.3.0) to
  complete captures with none. It also exposed a `<noscript>` screenshot artifact present since
  0.3.0, now fixed; the fixed capture was verified on a fixture, not re-measured live.
- An end-to-end skill run on a local fixture produced a derive build and a clone-base build that
  both pass `qa` with confirmed review, and validate-design passed 126 of 126 checks. Its frictions
  led to the Build contract binding and the run-log and review changes above.

These are single runs by LLM agents on one reference and one local fixture.

## Validate this checkout

From the repository root:

```bash
npm --prefix plugin/cli ci
npm --prefix plugin/cli run build
bash plugin/scripts/bootstrap.sh
~/.design-lens/bin/design-lens --version
```

The expected local version is `0.4.0`. Load this checkout's `plugin/` separately to use the
updated skills; older DESIGN.md and VARIATIONS.md files need the new tables before validation
passes. Repository checks are `npm --prefix plugin/cli run verify`,
`bash .harness/e2e-assert.sh --all` and `bash .harness/verify.sh --strict`. The release report
states the checks actually run and their results; the evaluation results are recorded in
[RESULTS.md](../../plugin/cli/test/evaluations/0.4.0/RESULTS.md).
